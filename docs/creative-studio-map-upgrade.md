# Official agency v2/v3 → dense creative studio v4

Automatic upgrade is disabled unless `DESKRPG_MAP_BACKUP_DIR` is an absolute path to an existing writable directory. Set it in the **Next.js process** environment only after mounting durable storage there. A container's writable layer or `/tmp` is not durable storage. Use a private directory owned by the application user (0700); each backup is written with mode 0600. Keep the mount when replacing containers.

Example deployment contract: mount a host backup directory at `/var/lib/deskrpg/map-backups` and set `DESKRPG_MAP_BACKUP_DIR=/var/lib/deskrpg/map-backups`. Provision and verify that directory before enabling traffic. The directory is not created automatically. Missing/unwritable storage, a failed fsync, or unavailable socket coordination leaves the old map unchanged.

Each eligible authorized channel GET writes a uniquely named JSON backup containing only `format`, `sourceCommit`, `channelId`, the selected `updatedAt`, and the original `mapData` value. SQLite JSON strings are preserved as strings; PostgreSQL objects are preserved as objects. The file is fsynced, renamed from `.pending`, and its directory is fsynced before any database mutation. Failed CAS attempts can leave harmless duplicate backups. Backup filenames hash the channel ID and include a random UUID; channel IDs never become filesystem paths.

The v2 fixture was generated from `git archive 5d836178 src` using that checkout's `buildOfficeEnvironment("agency")`, serialized with two-space JSON indentation and one final newline. Its SHA-256 is `d17e2d0a8e7900e2ad5cfe879c9dc406bcb9dbadc6fdedc2d85e42663fc9015f`. The first sparse v3 release is frozen as `official-agency-v3.json`; its SHA-256 is `276b0bdb5954b020e34d1efa7f8520a82dd749acea64e61b8bd5bdbefab034cd`.

Only a structurally exact official v2 or v3 map is eligible. JSONB object-key order is ignored; array order, dimensions, spawn, metadata and every object remain significant. The update writes only `map_data` and `updated_at`, conditioned on channel ID, a lossless database timestamp revision, and the selected map value. PostgreSQL uses `extract(epoch from updated_at)::text`, preserving microseconds independently of the session timezone; SQLite uses its raw timestamp text. The row timestamp token is internal to CAS. The public `mapRevision` is `map-sha256:<digest>` of canonical persisted map JSON: object keys are sorted recursively and array order is preserved. PostgreSQL JSONB and SQLite JSON produce the same map token. Channel renames and other metadata writes do not revoke an admitted map revision; actual map changes do. GET computes this token before restoring presentation-only tileset images. A lost race refetches the row; changed access fields trigger authorization again. Existing map configuration, profile assignments and saved homes remain stored unchanged.

Before persistence the Next process acquires a socket-server refresh lease (in-process registry in development; authenticated `POST /_internal/map-refresh` in production). It pauses channel events and publishes `map:refresh` protocol version 1, phase `begin`. On completion, including a lost CAS or write failure, it clears the cached layout, reservations, NPC continuations and player resume destinations, then publishes phase `ready`. Clients reload; creative-studio joins require the current `mapRevision` from an authorized channel GET and sanitize saved player positions. Empty/absent revisions are rejected using the legacy-compatible `join-error` event and server disconnect. An old cached bundle must be fully reloaded before it can bootstrap from GET and join the upgraded studio; it cannot regain authority simply by reconnecting. Supplied stale revisions receive `map:refresh/ready` without a spawn. The authorized NPC map response and socket authority share the same pure projection for runtime homes. Valid homes remain reserved; invalid creative-studio homes use available seats/free floor without updating NPC/profile rows. NPC off/on and update broadcasts use the same sanitized home. Every received motion snapshot updates the sprite's return/ambient home, including existing sprites. Reallocated creative-studio homes clear old positions, continuations and reservations; legacy maps retain their existing runtime-home behavior.

The lease assumes the existing single socket-authority deployment. Do not enable lazy upgrades across independent socket replicas. A socket transport failure after lease acquisition deliberately leaves that channel paused instead of resuming stale geometry. Restore transport and retry the same finish lease if available, or restart the socket process and reload affected clients after checking the persisted map. Do not restart it while a database update is still in flight. The API may have saved v4 even when its response reports a finish/transport error; inspect the row and backup first.

For rollback, disable `DESKRPG_MAP_BACKUP_DIR`, stop channel traffic, retain the current row as a second backup, and restore only `map_data` from the chosen backup with an optimistic check against the current row. Preserve the SQLite string/PostgreSQL object representation through the database adapter. Restart the socket process and reload clients. The previous renderer must remain shipped until rollback and edited-map compatibility are accepted. No template record is mutated: new agency selections use `deskrpg-office-v4:agency`, while other environments keep their existing tags.

Native PostgreSQL microsecond CAS and concurrent-save probes pass locally. Staging acceptance still needs a full production PostgreSQL GET migration, the configured durable mount, two open browser clients, and a saved-position/fixed-seat return check. Unit and SQLite tests do not replace that deployment check.
